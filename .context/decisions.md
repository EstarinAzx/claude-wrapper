- [[2026-08-01-a-refresh-must-not-blank-what-it-has]] — **#82**: the Agents dock re-reads its sidecars on the positive `turn-end` plus #80's nonce, and the read carries a **`keepStale` flag** because a session change and a same-session re-read want **opposite** things done to what is already on screen — `false` clears first (the previous session's agents under a new session's name is worse than nothing, and a failure has no earlier answer to fall back on), `true` is **stale-while-revalidate** and touches nothing until the new list is in hand, keeping the last good rows even when the read fails, because a transient error is not news worth destroying a correct snapshot over; the defect itself was **a dependency that could only change once** — `useChat` writes `setActiveSessionId` inside the `turn-end` branch, so `[sessionId]` moves `null → id` on turn ONE and the effect was **structurally incapable of firing** on turns 2..N, which is exactly the window where subagents spawn and nest, and the suite stayed green throughout because that effect *does* fire, just never twice; the naive second-dep fix was rejected because the effect is **destructive before it is productive** (`loading` ahead of every read, and a merge that drops disk rows unless `status === 'ok'`, so the tree shape flickers out and back at the one moment the user is watching it change); `LastTurn` is taken **whole** — the outcome decides WHETHER, the nonce decides WHEN, never `busy === false` since all three terminal outcomes clear it — and two non-obvious details are load-bearing: **the nonce is consumed whatever the outcome was** (else a stale one fires on a later render) and **seeded from the turn already ended at mount** (else opening the panel after a turn reads twice for one event); nothing else was built — no level-signal trigger (that is **#83**, and it needs the port + IPC chain), no `parentAgentId` on `LiveAgent`, no new `window.api` channel, and no `gui-82` driver because every surface here is React state over a channel jsdom already mocks; the suite had **zero** `toHaveBeenCalledTimes` before this, so its `toHaveBeenCalledWith` assertions were satisfied just as well by a trigger that never fired — seven tests added and four mutants killed, and the in-flight pin asserts the read really IS in flight before asserting the rows survived, because **an assertion that something SURVIVED is vacuous unless the thing it survives is shown to have happened**

- [[2026-07-31-the-window-waits-until-it-knows-where-to-be]] — #79 remembers the window's size and position in renderer `localStorage` (`window-bounds-v1`), pushed to main on mount, applied with `setBounds` **before the window is ever shown**, and it is a **chosen feature rather than a defect fix** (the record holds a measurement that nothing persists and no complaint that relaunching at 1100×780 costs anything); the obvious design is named and rejected by [[2026-07-31-a-preference-lives-where-it-is-read]] in those words, and the tempting counter — "main *reads* the bounds, so they belong to main" — dies on the shipped counterexample that `backgroundMaterial` is applied by main and stored by the renderer, so **main consuming a value does not make it the persistence owner**; what this ticket genuinely found is that bounds are the **first preference in the app that wants an answer before the window exists** (there is no apply-late-and-lose-a-frame option, because applying late is a window-manager *move and resize* of a window already on screen), which falsifies exactly one ADR sentence — "there is no structural difference between this preference and the four already stored" — while **reversing nothing**, since that ADR's own conclusion (construct hidden, tell it, then show) satisfies a constructor-time need with no store; the `win.show()` gate #78 **declined** is therefore **built here, for bounds only, and that is consistent rather than a flip-flop**: #78 declined it *as specified* ("gate on the renderer's first preference push" is a race between two independent messages and misses a third preference that crosses no boundary at all), whereas bounds are **one named message with one meaning**, so the readiness signal is a fact and the "protocol" #78 priced collapses to a `let` and a 1500ms timeout — generalising to **when a readiness gate looks expensive, check whether the expense is in the waiting or in defining what "ready" means**; measured by `gui-79.mjs` five runs A/B on **one build** (the probe defeats the gate by showing on `ready-to-show`, the line the app used to run): gated is **0ms visible at the wrong bounds, 5 runs of 5**, ungated is **0–49ms on 4 runs of 5** with an on-screen move+resize, at a cost of 7–45ms later appearance (139–149ms vs 102–138ms) — and **the ungated artifact being INTERMITTENT is what settled it**, since a window that lands somewhere different depending on machine load is worse than one that reliably takes a twentieth of a second longer; the clamp is a **safety** property rather than a validation one (a stored position promises a display layout that may not exist — undock a laptop and the window restores entirely offscreen with no way to reach it, strictly worse than not remembering) and its **identity case is the load-bearing test**, because a clamp that silently nudged valid bounds would satisfy every "it is on screen afterwards" assertion while making the feature pointless; the display list is read **when applying**, never cached at boot; two traps recorded — **a zero-arg `vi.fn()` mock makes its own `mock.calls[0][0]` a type error** (vitest infers an empty argument tuple, and `vitest run` does not typecheck, so the suite passes while `npm run typecheck` fails: **a loosely typed mock is not neutral, it is wrong in a direction**), and **an instrument can report a gate's success as the artifact** — `boundsChangesWhileVisible` first compared each visible sample against the previous sample regardless of ITS visibility, so the window being shown already-correct scored 1 for doing its job, the fourth instance here of **suspect the instrument first**; deliberately not built: maximised/fullscreen restore (bounds only — main reports `getNormalBounds()`, never `getBounds()`, so maximising cannot overwrite the remembered size), multi-window, and any migration of the four existing keys
